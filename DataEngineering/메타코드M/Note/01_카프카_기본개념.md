## 1. Kafka 등장 배경 

- 실시간 데이터 처리 필요성 증가

    - 예시: Linkedin 알림, IoT 시스템 로그, 새로운 Stock 거래 데이터 등 

- 과거 monolithic -> 마이크로서비스 아키텍처 등장

    - 서비스 간 데이터 흐름 복잡성 증가 

- 대용량 데이터 처리 요구

    - 데이터 처리 지연 발생 

- 이러한 문제를 해결하기 위해 LinkedIn에서 개발한 플랫폼이 Kafka. 

## 2. 이벤트 스트리밍 : 실시간 데이터 처리 기술 

- Event streaming ensures a continuous flow and interpretation of data so that the right information is at the right place, at the right time.

    1. 실시간으로 이벤트 소스에서 데이터를 캡처하고, 

    2. 이벤트 스트림을 지속적으로 저장하고, 

    3. 실시간 및 사후적으로 이벤트 스트림을 조작, 처리, 반응하며 

    4. 이벤트 스트림을 다양한 목적지 기술로 라우팅하는 실시간 데이터 처리 기술 

## 3. Apache Kafka란?

- 정의 : publish/subscribe 기반의 분산 Event Streaming 플랫폼 

    - 스트리밍 지속적 저장 (durable and reliable)

    - 스트림 처리 (real-time processing)

- 확장성, 안정성, 보안성 제공 

- 배포 환경: 온프레미스, 클라우드, 컨테이너, 가상 머신 등 

## 4. Kakfa 아키텍처 및 구성 요소 


### 4-1. 이벤트

- 소프트웨어 또는 애플리케이션에 의해 식별되거나 기록된 모든 종류의 동작, 사건 또는 변화를 말함 

    - 예시 : 결제, 웹사이트 클릭, 온도 측정 등 

- Kafka에서의 이벤트 (혹은 메시지)

    - Key/Value pair로 저장되는 데이터 조각 

    - 키: 메시지 식별자
    
    - Value : 메시지 내용 

    - 타임스탬프 : 메시지 생성 시간 


### 4-2. 배치 

- 카프카는 효율성을 위해 메시지를 묶어서 전송하는 배치 처리 방식을 사용 

- 배치 크기가 커지면?

    - 네트워크 전송 오버헤드를 줄여 시간 당 처리되는 메시지 수 증가 

    - 하지만 각각의 메시지가 전달되는 시간도 증가하는 Tradeoff가 있음. 

### 4-3. 스키마 

- 메시지의 구조를 정의하는 메타데이터 

- JSON, XML 등의 형식으로 정의되어 있음.

- 스키마 관리 도구를 사용하여 메시지 스키마를 정의, 관리, 공유할 수 있음. 

### 4-4. 서버 (브로커)

- 카프카 애플리케이션이 설치된 서버나 노드

- 퍼블리셔가 보낸 메시지를 일정 시간 저장하고, 토픽이라는 데이터 스트림으로 발행

### 4-5. 카프카, 카프카 클러스터 

- 브로커들의 집합

### 4-6. 클라이언트

- 프로듀서, 컨슈머 - 데이터를 쓰고 읽는 역할

- 다양한 프로그래밍 언어 지원 (Java, Python, Go 등)

### 4-7. 프로듀서

- 이벤트를 발행하는, 카프카로 메시지를 보내는 클라이언트 애플리케이션 총칭 

### 4-8. 컨슈머 

- 이벤트를 구독하고 처리하는, 카프카의 메시지를 꺼내가는 클라이언트 애플리케이션 총칭 

### 4-9. 주키퍼

- 카프카의 메타데이터 관리, 브로커의 Health Check 수행 

### 4-10. 메시지, 레코드

- 프로듀서 -> 브로커, 브로커 -> 컨슈머로 이동하는 데이터의 조각

### 4-11. 토픽 

- 메시지 피드들이 구분되는 논리적 단위 

- 이메일의 이메일 주소로 비유 가능 

### 4-12. 파티션 

- 토픽을 분할한 논리적 단위

- 병렬 처리 및 성능 향상을 위해 나눈 것 

### 4-13. 세그먼트(segment)

- 파티션 내 메시지를 저장하는 물리적 단위 

- 브로커의 로컬 디스크에 저장되는 파일
