# DAE (Data Analysis Engineer) 직무 이해

> 당근마켓 DAE의 역할, 기술 스택, 핵심 역량

---

## 핵심 인사이트 (3줄 요약)

1. **DAE = 데이터 엔지니어링 + 데이터 분석 하이브리드**
2. **목적: "분석하기 좋은 데이터 환경 설계"**
3. **핵심 도구: BigQuery + dbt + Airflow + Python/SQL**

---

## 1. DAE 역할 정의

### 공식 정의
> **"비즈니스 임팩트를 위해 분석하기 좋은 데이터 환경을 설계하는 사람"**

### 단순 데이터 엔지니어와의 차이

| 구분 | 일반 데이터 엔지니어 | 당근 DAE |
|------|---------------------|----------|
| 초점 | 파이프라인 안정성 | 비즈니스 임팩트 |
| 산출물 | 작동하는 파이프라인 | 분석가가 쓰기 좋은 DW/DM |
| 협업 대상 | 주로 엔지니어 | 분석가, PO, 비즈니스 팀 |
| 성공 기준 | 지연 없는 배치 | 비즈니스 지표 개선 |

### 핵심 역할

```
원천 데이터(Source)
      │
      ▼ (DAE가 설계하는 영역)
┌─────────────────────────────────────┐
│  데이터 웨어하우스 (DW)               │
│  - 원천 데이터 정제/표준화           │
│  - 데이터 품질 보증                  │
└─────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────┐
│  데이터 마트 (DM)                    │
│  - 분석가/PO가 쓰기 쉬운 형태        │
│  - 비즈니스 로직 반영                │
│  - 집계/지표 테이블                  │
└─────────────────────────────────────┘
      │
      ▼
   분석/리포트/ML
```

## 2. 기술 스택

| 기술 | 용도 | 면접에서 강조할 점 |
|------|------|------------------|
| **GCP BigQuery** | 메인 데이터 저장소 | 파티셔닝/클러스터링으로 비용 최적화 |
| **dbt** | 데이터 모델링/문서화 | SQL 기반 변환, 테스트, 버전 관리 |
| **Airflow** | 파이프라인 스케줄링 | Idempotency(멱등성) 보장 |
| **Python/SQL** | 데이터 가공/분석 | 복잡한 비즈니스 로직 구현 |

### dbt의 중요성 (가점 요소)

```
dbt(data build tool)가 특별한 이유:

1. SQL 기반 데이터 모델링
   - 분석가가 이해하고 수정 가능
   - 버전 관리(Git) 가능

2. 자동 문서화
   - 데이터 계보(Lineage) 자동 생성
   - 문서화 부담 감소

3. 테스트 자동화
   - not_null, unique, accepted_values 등
   - 데이터 품질 보증

4. 증분 모델(Incremental Model)
   - 변경된 데이터만 처리
   - BigQuery 비용 절감
```

## 3. 핵심 역량

### 3.1 데이터 모델링

**Star Schema 설계 능력**:
```
Fact Table (중심)
├── 측정값 (매출, 수량, 시간 등)
└── FK → Dimension Tables

Dimension Tables (주변)
├── 시간, 사용자, 상품, 위치 등
└── 분석 관점 제공
```

### 3.2 SQL 최적화

**필요 역량**:
- 윈도우 함수 (ROW_NUMBER, LAG, LEAD)
- 복잡한 JOIN 최적화
- CTE(Common Table Expression) 활용
- 집계/그룹핑 전략

### 3.3 데이터 품질 관리

**3단계 방어**:
1. 소스 데이터 검증 (스키마 체크)
2. 변환 중 검증 (dbt tests)
3. 결과 데이터 검증 (대시보드 모니터링)

### 3.4 비즈니스 이해

**필수 이해 영역**:
- 당근 비즈니스 모델 (광고, 거래)
- 핵심 지표 (DAU, 광고 ROAS, 거래 완료율)
- 데이터가 비즈니스에 미치는 영향

## 4. DAE가 해결하는 핵심 문제

### 문제 1: 분석가의 "데이터 추출 지옥"

```
상황: 분석가가 매일 비슷한 데이터를 추출 요청

DAE의 솔루션:
├── Self-service 대시보드 구축
├── 데이터 마트에 자주 쓰는 집계 테이블 생성
└── dbt로 문서화 → 분석가가 직접 SQL 작성 가능
```

### 문제 2: 지표 불일치

```
상황: 팀마다 같은 지표도 다른 숫자가 나옴

DAE의 솔루션:
├── Single Source of Truth 구축
├── dbt로 지표 정의 버전 관리
└── 데이터 거버넌스 문서화
```

### 문제 3: 빅쿼리 비용 폭증

```
상황: 비효율적인 쿼리로 비용 급증

DAE의 솔루션:
├── Materialized View 구축
├── 파티셔닝/클러스터링 최적화
└── 쿼리 리뷰 프로세스 도입
```

## 5. 당근 DAE의 특별한 도전

### 도전 1: 로컬 데이터의 복잡성

```
하이퍼로컬 광고를 위한 위치 데이터:
├── GPS 좌표 (실시간)
├── 등록 동네 (사용자 설정)
├── 광고주 희망 반경 (3km, 5km 등)
└── 상권 경계 데이터

→ 위치 기반 매칭 알고리즘 최적화 필요
```

### 도전 2: 실시간성 vs 비용 균형

```
요구사항:
- 광고 노출은 실시간 (밀리초 단위)
- 분석은 배치로 충분

DAE의 설계:
├── 실시간 스트림 (광고 서빙용)
└── 배치 집계 (분석용)
→ 적절한 데이터 분리 설계
```

### 도전 3: 다양한 버티컬 통합

```
중고거래 + 알바 + 부동산 + 중고차:
├── 각 도메인별 특화 데이터
├── 통합된 사용자 프로필
└── 크로스 도메인 추천

→ 통합 데이터 모델 설계 필요
```

## 면접 답변 가이드

### Q: "DAE와 일반 데이터 엔지니어의 차이는?"

**답변 프레임**:
```
"일반 데이터 엔지니어는 '작동하는 파이프라인'에 초점을 맞춥니다.

DAE는 '분석가가 쓰기 좋은 데이터 환경'을 설계합니다.

구체적으로:
1. 비즈니스 로직이 반영된 데이터 마트 구축
2. dbt로 문서화/테스트하여 분석가가 신뢰하고 사용 가능
3. 비즈니스 지표 개선을 직접 측정하는 역할

당근에서는 광고 ROAS나 거래 매칭 품질 개선에 
데이터 인프라가 직접 기여하는 것이 DAE의 성공 기준입니다."
```

### Q: "dbt를 왜 쓰나요?"

**답변 프레임**:
```
"3가지 이유에서 dbt를 적극적으로 사용합니다:

1. SQL 기반: 분석가가 직접 수정 가능
2. 자동 문서화: 데이터 계보(Lineage)가 자동 생성됨
3. 테스트 자동화: not_null, unique 등 품질 검증 자동화

당근처럼 빠르게 성장하는 환경에서 
데이터 거버넌스와 협업 효율성이 매우 중요합니다."
```
